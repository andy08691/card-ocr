# 混合架構擴充計畫（Hybrid Scaling Plan）

> 目標：面向 **1000 DAU × 5 張/天 = 5,000 張/天**，讓使用者上傳名片後
> **每人只等 ~5 秒**，且能吸收「展場散場」等突發大量。
>
> 策略：**自建 1 張 GPU 常備（平時便宜）+ 雲端 GPU 依需求 burst（爆發時彈性）+
> 非同步佇列（防炸、體感順）+ 全程熱模型（不冷啟）**。
>
> 建立日期：2026-09-02　｜　**狀態：已擱置（2026-09-04）**
>
> ⚠️ **這份計畫的前提已不成立。** 它是為 5,000 張/天 設計的；實際預估用量只有
> **100–200 張/天**，低了一個數量級，所以「自建 5 個月回本」的結論不再有效。
> 現行方案改走 **`cloud/` 雲端管線**（`gpt-5.6-luna`，無需 GPU），
> 見 [`cloud/README.md`](cloud/README.md)。
> 本文保留作為「量真的長到那個級距時」的參考。

---

## 0. 核心原理（先懂這個，架構才有意義）

> **「等待 ~5 秒」= 服務速率必須 ≥ 到達速率。**
> 佇列（queue）只能防止當掉/逾時，**不能減少延遲**。
> 若同一秒湧入的請求超過處理能力，最後那個人一定等很久——這是排隊理論。

所以「突發也只等 5 秒」靠三件事組合：
1. **榨乾單卡吞吐** → vLLM continuous batching。
2. **非同步架構** → 突發能安全排隊、HTTP 不卡死。
3. **容量對準尖峰**（非平均）→ 平時自建扛，真爆發時雲端補。

## 1. 容量規劃（先估尖峰，再配容量）

| 情境 | 到達率 | 維持 ~5s 所需「有效處理速率」 | 需要的卡 |
|---|---|---|---|
| 平均（5000 / 24h） | ~0.06 張/秒 | 極低 | 單卡閒置 |
| **忙碌時段**（全日 20% 集中 1 小時，次分鐘突發 ~2–3×） | ~1 張/秒 | ~1 張/秒 | **1 張 batching GPU 就夠** |
| **同步大爆發**（200 人 30 秒內同時掃） | ~6–7 張/秒 | ~6–7 張/秒 | 需 5–7 卡（**不常備，用雲端 burst 吸收**） |

**吞吐基準：**（實測數據見 [`benchmarks.md`](benchmarks.md)：Mac ~16.6s、L4 ~5.2s/張）
- 目前程式（全域鎖 `_ocr_lock`、一次一張）：**~12 張/分（~5s/張，L4 實測）**。
- 改 vLLM server 模式（continuous batching）：**單卡約 2–4×**（實際待 benchmark 釘死，取決於 VRAM 餘裕；MinerU 模型僅 1.2B，24GB 卡可同時塞多張）。

**結論：** 99% 的日子（忙碌時段等級）→ **1 張會 batching 的 24GB GPU 就能每人 ~5 秒**。
真正的同步大爆發 → **非同步 UX + 雲端 burst** 優雅吸收，不為此常備閒置硬體。

## 2. 架構總覽

```

使用者 ─ 負載平衡 ─┤        ...(可水平多開)         ├─┐

                         │  上傳→存圖→丟佇列→立刻回 job_id (<200ms)
                         ▼                                 │

                  │ Redis 佇列   │◀────────────────────────┘
                  └──────┬───────┘
            (依佇列深度 autoscale worker)

   ┌─ GPU Worker 1 (自建) ┐  ┌─ GPU Worker 2..N (雲端 burst) ┐
   │ MinerU vLLM server   │  │ 同一份 deploy/Dockerfile        │
   │  + Ollama qwen3:4b   │  │ min=0，依佇列深度自動起停       │
   │ (模型常駐、永遠熱)    │  │                                 │

              │  結果寫 DB + 原圖存物件儲存   │
              ▼                              ▼

     └─────────────┘              └─────────────────────┘
              ▲
   前端輪詢 GET /jobs/{id}（或 WebSocket 推播）拿結果
```

## 3. 流程（Request Lifecycle）

### A. 上傳（同步、極快，<200ms）
1. `POST /api/cards/upload` 收到圖片。
2. 存原圖到**物件儲存**，寫一筆 job（狀態 `queued`）。
3. 把 job 丟進 **Redis 佇列**。
4. **立刻**回傳 `{ "job_id": ..., "status": "queued" }`。
   → 突發時 HTTP 連線永不卡死。

### B. 辨識（背景 worker）
5. GPU worker 從佇列取 job，狀態改 `processing`。
6. `run_ocr()`（MinerU **vlm-http-client** → 常駐 vLLM server，continuous batching）。
7. `extract_card()`（candidate → 本地 Ollama LLM → validator → repair）。
8. 結果寫 DB、狀態改 `done`（失敗則 `failed` + 錯誤訊息）。

### C. 取結果（前端）
9. 前端上傳後顯示「已收到，辨識中…」。
10. 輪詢 `GET /api/jobs/{job_id}`（或 WebSocket 收推播）。
11. `status=done` → 顯示 10 欄位；使用者可手動修正（既有 PUT API）。

### D. 突發時的自動擴充
12. 監控 **佇列深度**；超過門檻（如 > 20）→ autoscaler 在雲端起 burst worker。
13. 佇列清空、閒置一段時間 → burst worker 自動關閉（min=0，省錢）。

## 4. 元件清單（要建構的環境）

| 元件 | 選項 | 用途 | 狀態 |
|---|---|---|---|
| **App / API 層** | FastAPI（現有）｜可多副本、無狀態 | 收上傳、發 job_id、查結果 | 需改：上傳改非同步 |
| **佇列** | Redis（+ RQ / Celery / arq） | 緩衝突發、派工給 worker | 新增 |
| **GPU Worker** | 自建 1 台 + 雲端 burst | MinerU vLLM server + Ollama，跑辨識 | 需改：vLLM server 模式、拿掉鎖 |
| **vLLM server** | MinerU `vlm-http-client` 後端 | continuous batching，單卡吞吐最大化 | 新增 |
| **物件儲存** | Cloudflare R2 / AWS S3 / 自架 MinIO | 存原圖（會長很快，見 §5） | 新增 |
| **DB** | 先 SQLite → 量大再 PostgreSQL | 存辨識結果 | 現有，暫不改 |
| **負載平衡 / 對外** | Cloudflare Tunnel（免費 HTTPS）/ Nginx | 對外入口、TLS | 新增 |
| **Autoscaler** | RunPod serverless / Modal / K8s HPA | 依佇列深度加減 burst worker | 新增（第二階段） |
| **監控** | Prometheus + Grafana / 雲端內建 | 佇列深度、P95 延遲、GPU 使用率 | 新增 |
| **UPS 不斷電** | 自建機房必備 | 防跳電損毀 | 硬體採購 |

### 5.2 雲端 burst worker（只在爆發時付費）

| 平台 | GPU | 計費 | 特性 |
|---|---|---|---|
| RunPod serverless | RTX 4090 / L4 / A10 | 每秒計費，min=0 | 冷啟需 warm pool 或掛 Volume 快取模型 |
| Modal | L4 / A10 / A100 | 每秒計費 | Python-native，autoscale 好寫 |
| GKE + GPU 節點 | L4 | 節點小時計費 | 想全 K8s 化再考慮 |

- 用**同一份 `deploy/Dockerfile`**，環境變數一致。
- 冷啟動是 5s 承諾殺手 → burst worker 掛 Volume 快取模型、或保留 min=1 warm。
- 概估：L4 ~US$0.5/hr、4090 ~US$0.7/hr，**只有爆發時段起跑**，每月多花通常幾百~幾千 NT$。

### 5.3 每月營運成本（平時）

| 項目 | 每月 NT$ | 說明 |
|---|---|---|
| 電費（自建機） | ~600–1,000 | 平均 ~180W（多時間閒置），台電 ~NT$4/度 |
| 物件儲存 | ~100–500 | R2/S3；隨保留天數與量成長（見下） |
| 網域 | ~30 | 一年 ~NT$400 |
| 對外連線 | 0 | Cloudflare Tunnel 免費 HTTPS |
| 雲端 burst | 變動 | 只在爆發時計費 |
| **平時合計** | **~NT$1,000–1,500/月** | 爆發月往上浮動 |

> **儲存爆量提醒** ⚠️：5,000 張/天 × ~0.7MB ≈ **3.5GB/天 ≈ 1.3TB/年**。
> → SSD 至少 2TB；原圖處理完設**保留天數自動刪除**，或直接存物件儲存 + 生命週期規則。

### 5.4 自建 vs 全程租雲端

| 方案 | 前期 | 每月 | 一年總計 |
|---|---|---|---|
| **混合（自建 + burst）** | ~NT$57,000 | ~NT$1,000–1,500 + 爆發 | **~NT$72,000（第一年）**，之後只電費 + 少量 |
| 全程租 L4 常開 | 0 | ~NT$11,000 | ~NT$132,000/年 |

→ 24/7 常開時，**混合方案約 5 個月回本**，之後每年只花電費 + 少量雲端/儲存。

### 5.5 與雲端 VLM 管線的交叉點（2026-09-04 補）

`cloud/` 管線每張約 **US$0.0017（NT$0.055）**，無前期投資、無電費、無 UPS。
自建方案要跑到多大的量才划算：

| 比較基準 | 自建每月 | 交叉點 |
|---|---:|---|
| 只比 GPU 機的**營運成本**（電費 + 儲存） | NT$1,250 | ≈ 22,700 張/月 ≈ **757 張/天** |
| 加上硬體 3 年攤提（NT$57,000 / 36） | NT$2,833 | ≈ 51,500 張/月 ≈ **1,716 張/天** |

實際用量 100–200 張/天 → 雲端每月 NT$456–576（含 VPS），**第一年約便宜 10–16 倍**，
而且硬體永遠回不了本。量成長到 ~1,700 張/天 以上時，再回頭執行本計畫的 Phase 1。

## 6. 要改的軟體（比硬體更關鍵）

1. **上傳改非同步**：`POST /upload` 只做「存圖 + 丟佇列 + 回 job_id」；新增 `GET /jobs/{id}`。
2. **MinerU 改 `vlm-http-client` 後端**，連常駐 vLLM server → 啟用 continuous batching。
3. **拿掉/放寬 `_ocr_lock`**（`app/services/ocr.py:156`）→ 由 vLLM server 統一調度批次。
4. **模型永遠熱**：vLLM 常駐、Ollama `keep_alive=-1`；worker 就緒探針（readiness）沒熱不進流量。
5. **前端 UX**：上傳後立刻「已收到，辨識中…」+ 進度；結果幾秒後填入（尾端偶爾等 15s 體感也 OK）。
6. **物件儲存 + 保留策略**：原圖進 R2/S3，設 N 天自動刪。

## 7. 監控指標（決定何時加卡）

| 指標 | 看什麼 | 行動門檻 |
|---|---|---|
| 佇列深度（queue depth） | 積壓程度 | 持續 > 20 → 起 burst worker |
| P95 端到端延遲 | 使用者實際等待 | 持續 > 10s → 容量不足，加 worker/卡 |
| GPU 使用率 / VRAM | 單卡是否吃滿 | 長期 > 80% → 該加常備卡 |
| worker 錯誤率 | 穩定度 | 上升 → 查 OOM / 模型 / 依賴 |
| 儲存用量 | 磁碟成長 | 逼近上限 → 調保留天數 / 擴容 |

## 8. 實作 Roadmap（可勾選追蹤）

### Phase 1 — 單卡榨滿 + 非同步（CP 值最高，先做）
- [ ] 上傳 API 改非同步：`POST /upload` 回 `job_id`、新增 `GET /jobs/{id}`
- [ ] 導入 Redis + 工作佇列（RQ / arq / Celery 擇一）
- [ ] worker 進程：消費佇列 → `run_ocr` + `extract_card` → 寫結果
- [ ] MinerU 切 `vlm-http-client`，起常駐 vLLM server（釘 `vllm==0.10.2`）
- [ ] 放寬 `_ocr_lock`（改 semaphore 或交給 vLLM 批次）
- [ ] Ollama `keep_alive=-1`、worker readiness 探針
- [ ] **Benchmark**：單卡 batching 實際吞吐（釘死 §1 的 2–4× 數字）
- [ ] 前端：上傳→輪詢→顯示的非同步 UX

### Phase 2 — 儲存與對外
- [ ] 原圖改存物件儲存（R2 / S3 / MinIO）+ 保留天數自動刪
- [ ] Cloudflare Tunnel 對外 HTTPS（或 Nginx + 憑證）
- [ ] DB 備份排程（`card_ocr.db` / PG；含個資加密與存取控管）

### Phase 3 — 雲端 burst 與自動擴縮
- [ ] 用 `deploy/Dockerfile` 建 burst worker 映像 + Volume 快取模型
- [ ] 選平台（RunPod serverless / Modal）接同一 Redis 佇列
- [ ] autoscaler：依佇列深度起停 burst worker（min=0 或 min=1 warm）
- [ ] 壓測：模擬同步爆發，驗證 P95 落點

### Phase 4 — 觀測與韌性
- [ ] 監控（Prometheus + Grafana / 雲端內建）：佇列、P95、GPU、錯誤率
- [ ] 告警（延遲 / 錯誤率 / 磁碟）
- [ ] （選）第二張常備卡或雲端備援達成 SLA

## 10. 一句話總結

硬體只要 **1 張 24GB GPU（~NT$57k）**；真正讓「突發也只等 5 秒」的是
**vLLM batching（榨單卡）+ Redis 非同步佇列（防炸、體感順）+ 雲端 burst（吸收真爆發）+
全程熱模型（不冷啟）**。**先做 Phase 1** 就能讓單卡在忙碌時段穩定 ~5 秒。
